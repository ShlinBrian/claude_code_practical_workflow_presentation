沒有可驗收的 DoD，agent 只會繞圈或自我感覺良好地停下。

預設直接丟，失敗了再回來問「為什麼」

結果不好時，問的不是「我該怎麼補刀」，而是——

為什麼 agent 自己到不了？

四個常見根因，分屬兩側

診斷：agent 到不了的四個原因

  • code看不懂我們寫的程式
  • code缺 domain knowledge
  • code無法 mapping 需求到應該修改的邏輯
  • briefprompt 沒講到重點 / 沒有完成定義
處方也分兩軌——不能只加註解

兩軌處方

Code 側 · 會複利
加註解
↓加 mapping index
↓重構段落
Brief 側 · 你不可外包
寫成可測的 goal（DoD）
↓補背景與邊界
↓整理成可交辦的 brief
兩軌的關係 = 整份報告的閉環

Code 側會複利，Brief 側人來扛

Code 側把 codebase 改造得更 agent-legible，會隨 agent 變強而複利。

Brief 側不會被 agent 自動補上，是人永遠要扛的部分。

為什麼 brief 側 agent 補不了

AI 是一面鏡子

它會挑戰你的內容，但不會質疑你的意圖。

你餵它模糊，它就把沒想清楚的指令原封反射回來。
頂多把申論題變成填空題，空格還是你來填。

它能幫你問，沒辦法替你想。

把流程編碼成 skill，讓團隊都能用

Superpowers：流程 → Skill

Jesse Vincent · 2025/10

問題不在 Claude 的能力，在缺專業開發流程。
把 brainstorm → plan → TDD → review 編碼成 skills。

簡單任務 → 跳過流程

typo、小函式：goal 直接做

中大型 → 流程才划算

多檔、越改越歪：流程紀律拉開差距

判斷軸 = 做錯重來貴不貴，不是人資不資深

skill 不是銀彈，兩道圍欄

幫你問 ≠ 替你想

1. 餵模糊進去，會產出結構漂亮的錯任務——比明顯的爛 prompt 更難抓。

2. DoD 的品質仍靠 domain knowledge。Skill 幫你把 DoD 寫下來，不能替你判斷 DoD 對不對。

正面：思考外包不了，但流程可以編碼、教會整個團隊。

ACT 03

證據與實踐

一個真實案例、一份成本帳、知道何時別自動化

前面講的方法論，跑起來長什麼樣？

壓力測試：一個夠大夠難的真實任務

案例：MSSQL → PostgreSQL Migration

在系統底層換掉引擎，
但每一個對外行為都得一模一樣。

難不在需求模糊，在三件事疊加

為什麼這是硬骨頭？

1. SQL 方言散落整個 stack — SELECT TOP · [dbo]. · (NOLOCK) · ISNULL

2. 結構性差異 — 49 proc / 4 view，SCT 只有 GUI 沒自動化

3. 型別 + 大小寫靜默出錯 — 一個沒對齊就不報錯但答案錯

最難的不是「跑不跑得起來」，而是「答案對不對」。

讓方法論落地的關鍵：有一個 oracle

這次的完成定義

DoD = Oracle

逐 endpoint、逐 row，跟 golden MSSQL 做 A/B 比對。

這就是讓 loop until goal 有意義的那個 oracle。
沒有它，agent 不知道自己有沒有做對。

結論：goal 與 workflow 都能完整跑完

兩個值得記住的觀察

成本觀察

觀察 1

掛上 skill ≠ 用到 skill。
workflow_skill subagent 有用 → 最便宜；goal_skill 掛了沒用 → 最貴（cache_read 24.3M，純浪費）。

觀察 2

錢主要花在 cache_read。
長 autonomous loop 的固有成本。Hygiene 只能邊際壓低，但邊際也是錢。

知道什麼時候不用，跟知道怎麼用一樣重要

什麼時候不要直接自動化

  • 沒有可自動驗收的 oracle
  • 需要不可逆的副作用 — 刪資料、打外部 API、動錢
  • domain knowledge 不在 repo 裡
瓶頸從「寫 code」搬到「review PR」

Human review 是新瓶頸

PR 動了 DAO、config、49 個 procs→functions、39 處修正。

對策：逼 agent 拆小 PR + 自帶 A/B 證據。
讓人 review 的是證據，不是逐行 diff。

邊際槓桿：降低重複讀 context 的成本

Checklist

下 /goal 或 /workflow 前的五句自問

  1. 完成定義
    有沒有能自動檢查的「做完」？沒有 oracle 就先別跑。
  2. 目標
    要的是成品與決策，還是只寫了一個動作？
  3. 邊界
    哪些不要碰？不可逆副作用先圈起來。
  4. 可讀性
    agent 看得懂嗎？缺 mapping 就先補（會複利）。
  5. 階段
    現在要它想、比、決，還是做？
一句話總結

機器側會越來越強，
人側不會自動補上。

不要問「agent 現在能不能做」，
要問「我能不能把目標與環境
整理到讓 agent 自己能做」。

把人從執行者，挪到 把任務定義清楚的人 與 把 code 變好懂的人。
這兩件事 agent 替不了，每一次投資都會隨它變強而複利。
