A Practical RD Workflow

One reproducible workflow that turns a requirement into a result you can trust:
brainstorm → spec with a Definition of Done → /goal or /workflow → verify with an oracle.

The one idea behind everything that follows

Stop asking the wrong question

❌ “Can the agent do it?” Polishing prompts plateaus. You wait for a better model.
→
✅ “Have I defined the task and the environment well enough that it can?” The leverage is the spec, the definition of done, and the workspace you hand it.

Everything in this talk is one of those two levers.

What it looks like on the migration task

"Migrate the DB" → a spec

"keep everything working" = same API responses, or same DB state? Same HTTP responses, byte-for-byte where data allows. How do we verify that automatically? A/B every endpoint vs a golden MSSQL, row-by-row. → committed: docs/specs/mssql-pg-migration-design.md (with DoD)

A committed spec with a testable DoD — exactly what /goal & /workflow consume.

The method, part 2 — two ways to spend tokens well

/goal — loop until the goal is met

# hand it the spec + a machine-checkable goal:
/goal All endpoints return 200 AND each A/B-matches
  golden MSSQL row-by-row. Spec: …migration-design.md
build → test → A/B → fix → repeat until the oracle passes

Only works if the goal is machine-checkable. No oracle → it loops or stops on a vibe.

/workflow — orchestrate many agents deterministically

/workflow — multi-agent fan-out

// convert 48 stored procedures in parallel, then verify each
const procs = await agent('list all .sql procs', {schema: PROCS})
const results = await pipeline(
  procs.list,
  p => agent(`convert ${p} MSSQL→PG`, {phase: 'convert', isolation: 'worktree'}),
  c => agent(`A/B verify ${c.proc} vs golden`, {phase: 'verify', schema: VERDICT})
)
return results.filter(r => r.verdict.faithful)

Each proc flows convert→verify independently. Wall-clock = slowest chain, not the sum.

Not rivals — pick by the shape of the work

When each fits

/goalone coherent objective · tight feedback loop · mostly sequential (build/test/fix)
/workflowmany independent units (N procs) · want parallelism + isolation · deterministic structure

Hybrid (most realistic): a main-loop /goal drives build/deploy/A-B and calls /workflow to fan out the 48 proc conversions.

The experiment's C1-vs-C2 gives this decision real data.

Knowing when NOT to automate matters as much

When not to automate directly

No oraclenothing machine-checkable to loop against
Irreversible side effectsdeleting data · external APIs · moving money
Domain knowledge not in the repothe agent can't read what isn't written down

Human review is the new bottleneck → force small PRs that carry their own A/B evidence. Review the evidence, not every diff line.

Pre-flight Checklist

Five questions before you type /goal or /workflow

  1. Definition of done
    Is there a machine-checkable "done"? No oracle → don't run yet.
  2. Goal
    Do you want a deliverable and a decision, or did you just describe one action?
  3. Boundaries
    What's off-limits? Fence irreversible side effects first.
  4. Legibility
    Can the agent understand the code? Missing a map → add it first (it compounds).
  5. Stage
    Do you want it to think, compare, decide, or do right now?
