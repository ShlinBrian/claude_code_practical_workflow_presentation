Three layers of engineering an agent

Prompt the words
Harness ◆ today

Today is all about the harness — because it is what earns you the autopilot that comes next

先給大家一個overview來了解我們今天的主軸。
跟 AI 一起開發，其實是一條路，三個階段，一階比一階更自主：
**第一階 Prompt**：我們用單次互動寫出精準指令，把「這一次」的結果做對。
**第二階 Harness**：不只是下指令，
讓任務、完成的定義、工作環境都被定義得夠清楚，讓agent能 *自我驗證*。
我們都知道，這就是最麻煩的地方，所以我們今天會介紹有哪些簡單好用的工具或指令來幫我們。
**第三階 Autopilot 也就是這條路的終點，也就是最近常聽到的loop engineering**：
把前面這些包成一個 *自主運作* 的系統，就可以讓 agent 進入 全自動駕駛。
Agent可以：
1. 拿新任務
2. 定義任務
3. 處理任務
4. 交付任務
就這樣一直loop下去。
而我們今天，把力氣花在 harness，為的就是有一天我們能把 loop 建立起來，真正的通往 Autopilot。
Stop asking — “Can the agent do it?” Tune the prompts · switch to a better model · hit a ceiling
↓
Start asking — “Have I defined it well enough that it can?” The task, the definition of done, the workspace you hand it

Define it that well and the agent can run it on its own — that's the autopilot

(上面亮)
我們現在最前沿的 model 基本上強到可以執行任何事情。 所以我們其實不用再去想 「這個 agent 做得到嗎？」

這就是我們身為稍微懂一點程式的人類，現在應該要做的事情。
Chapter 01

Everyday hygiene

第一章先從幾個小習慣開始，這些是今天回去馬上就能用的東西，門檻最低、回報也最快。 它們同時也是後面所有東西的基礎：context 管得乾淨、交接寫得清楚，之後 agent 才有辦法自己接手、自己跑。

You shouldn't have to repeat yourself

The pain
- Context filling up
- Usage running out
- The agent forgets an earlier decision
⇒ Need to re-explain the whole thing
→
The fix
- Shape the live context (/rewind, /btw, subagent)
- Hand state off before context/usage runs out
- Flush clean, useful memory to CLAUDE.md
⇒ Steer it, don't restart it
（左邊亮）
大家應該都遇過：跑到一半 context 快滿了、usage 快用完了，或是 agent 開始變笨忘記你前面講過的決定。 結果就是把整個任務從頭再解釋一遍。
（第二下：右邊亮、左邊暗）
解法有三個方向：
1. 是在執行過程中主動控制 context，等一下的 /rewind、/btw、subagent 就是在做這件事
2. 是在 context 用完之前，先把狀態交接出去。
3. 是收尾的時候，把值得留的決定寫進 CLAUDE.md，下個 session 一開始就知道。
這樣你是在指揮它，而不是每次都重來。

Keep the run on track

# wrong turn? rewind to before it — no re-explaining
/rewind → pick the <checkpoint> before the bad edit

# quick lookup you DON'T want in history — answer shows
/btw what does this driver error mean?

# offload a noisy task to a fresh context — only the result returns
create a subagent to test the modified modules and return only the fail ones

/rewind back out · /btw look up without growing context · subagent type an instruction to spin one up

在執行過程中：
/rewind：當你發現 agent 開始走錯方向，或是你後悔剛剛你下的prompt，直接 /rewind，就可以 rollback 到你想要的 checkpoint。
/btw：跑到一半想查個小問題，又不想讓它進到對話紀錄，可以使用 /btw，他會將答案顯示在一個可以關掉的視窗裡，不佔用你現在 session 的 context。
subagent：我們可以呼叫建立一個 subagent，來去進行一些跟主任務比較不相關的工作，像是請他「測試那些剛修改完的 modules 然後只回傳失敗的」，這樣只有結果會被傳回 session 當中。
透過這些方法，我們就可以保持這個 session 當中的對話，都是有意義的資訊

再來是 session 收尾的時候，把值得留的東西存下來。
像是UI或是程式風格的修改，如果改完你覺得不錯，就在完成的最後說「把剛剛這個設計存成規則寫進 CLAUDE.md」

Chapter 02

The method

接下來進到今天的重心：定義任務的方法。

The naive way

# the prompt most people would write:
Migrate this Java service from MSSQL to PostgreSQL.
  Keep everything working.

Looks reasonable It is a trap

我們都喜歡把事情簡單化，都很想直接丟一句話給 agent，然後拿到可以上線的東西。
例如說：「把這個 Java 服務從 MSSQL 搬到 PostgreSQL，保持一切正常運作。」
看起來很合理，有任務、也有目標，但你會得到什麼樣的結果？

What you get back

It rewrites the SQL, swaps the driver, the build goes green — and it confidently says "done."

Three things are missing — and they're the whole game:

No spec“keep everything working” is undefined
No definition of donenothing checks the answers are still correct
No isolationit edited your working tree in place
agent 會認真地改 SQL、換 db driver，build 過了，然後說「完成了」。從它的角度看，它確實完成了。
但我們不喜歡，不喜歡的原因就是缺少了 spec, 完成的定義 以及環境：
一，沒有規格——「保持一切正常」沒有定義。
二，沒有完成的定義——沒有任何東西在檢查答案對還不對。
三，沒有隔離——它直接改了你的工作目錄。
這三個洞，就是接下來的方法要補的。

整條流程最關鍵的就是 brainstorming，我們可以利用它來幫我們把任務定義清楚

★ brainstorming

Five steps, one gate at the end

01  Explore project context
↓
02  Ask clarifying questions — one at a time
↓
03  Propose 2–3 approaches with trade-offs
↓
04  Present design, approve section by section
↓
05  Commit a spec — with a Definition of Done

Refuses to write code until the design is approved That gate is the point

brainstorming 有五個步驟：1. 摸清專案脈絡、2. 一次問一個問題、3. 給兩三個方案和取捨、4. 設計分段讓你確認、5. 最後 commit 一份帶 Definition of Done 的規格。
重點在最後那道關卡：設計沒被確認，它就不寫 code。
它強迫的正是我們最常跳過的那一步——先想清楚再動手。
前面多花十分鐘，換的是後面少掉的重寫和 debug。

"Keep everything working" → questioned into a spec

這邊截圖給大家看一下brainstorming 的實際畫面。
我們把剛剛那句「把服務從 MSSQL 搬到 PostgreSQL，保持一切正常」真的丟進 brainstorming 之後。
它不會直接開工，而是先摸清專案，然後一題一題反問：
第一，「保持一切正常」的驗收標準是什麼、要怎麼證明搬對了？
第二，PostgreSQL 的 schema 跟資料從哪來？
第三，這次要涵蓋哪些範圍？
每回答一題，模糊的需求就被逼出一塊可測試的定義。
最後就會逐題被問成一份帶有 完成定義 的規格。

規格定義好之後，通往 autopilot 有兩條路，兩條都是從 SuperPowers 出發。
路 A：直接用 SuperPowers 把整條 lifecycle 走完——spec → plan → TDD → review → verify，讓它自己把任務從頭扛到尾。
路 B：把 SuperPowers 產出的那份規格，餵給 /goal 或 /workflow 這類 loop 工具，讓它們拿著規格去迴圈——一個是循環到目標達成，一個是多個 agent 平行展開。
看卡片下面的範例：/goal 你給它一個機器可檢查的目標加上規格，它就一直 build → 測試 → 修，跑到裁判通過；/workflow 你用一句自然語言下指令，它會展開成很多平行的獨立單位，各自處理再各自驗證。
重點是——不管走哪一條，最後都通往同一個地方：autopilot。你只要用自然語言把要做的事講清楚，剩下的它們來做。下一頁講這件事會通往哪裡。

Where this leads

Once the spec is defined,
/goal and /workflow take it and run Define it well enough to run on its own
⇒ autopilot

把前一頁那兩個工具拉高一層來看：它們共同的前提，就是前面那份帶 DoD 的規格。 規格定義好，/goal 和 /workflow 就拿著它去跑；定義得夠清楚、有機器可檢查的裁判，agent 才能一直自己跑下去。 而這正是自動駕駛的前置條件——規格好到它能自己驗證、自己收斂，你才敢放手讓它自動運行。

But first — build the verifier

Both tools are self-verifyingthey loop against a verifier — only as reliable as the verifier you give them
No verifier yet? Build it firstit's step one, not the last step — thin coverage means the loop runs blind

If you can't verify it, don't ship it

在放手讓它自動跑之前，有一個前提要先講清楚。 /goal 和 /workflow 都是靠裁判在自我驗證，所以它們的可靠度，就等於你給它的那個裁判的可靠度。 有些任務的裁判是現成的——舊系統的正確答案本來就存在，拿來比對就好，等一下第三章的案例就是這種；但平常的功能開發沒有現成答案，裁判就是你的測試，得自己先蓋出來。 所以驗證器是第一步，不是最後一步。覆蓋不夠，這個迴圈就是在盲跑，跑出來的東西你沒辦法信。Anthropic 的說法是：驗證不了的東西，就不要出貨。
Chapter 03

The case

方法講完了，大家可能會想：這在真的很難的任務上行得通嗎？ 接下來用一個我實際做完的案例來看難度在哪。

Not a "swap the JDBC driver" job

What

A live downloader backend — dispatches software builds to users and logs each download:

trial patch subscription OEM digital

In production every day, on MSSQL → PostgreSQL.

The bar

Every API must return the correct answer on PostgreSQL.

Dispatch the wrong build → a real user downloads the wrong file.

先講清楚這個案子是什麼。這不是換個 driver 就好的事。 這是一個叫 downloader 的後端系統，還在線上跑——它負責把各類軟體 build（試用版、patch、訂閱版、OEM、數位版）派送給使用者，並記錄整個下載歷程。它不是管能不能下載，而是解析出對應的正確 build、把下載連結準備好提供給官網跟 downloader 程式，使用者再從那裡取得檔案。整套從 MSSQL 搬到 PostgreSQL：資料、schema、stored procedure，還有埋在 Java/JSP 裡的方言 SQL。 標準只有一個：每支 API 在 PostgreSQL 上都要回傳正確的結果，因為派送錯的 build，使用者就會下載到錯的檔案。

The scope, at a glance

~390k rows · 23 tables · 48 stored procedures · 4 databases

1 · Move the schematables & stored procedures rebuilt on PostgreSQL
→
2 · Move the dataevery row copied over from the old database
→
3 · Move the codethe app's SQL rewritten to speak PostgreSQL

The hard part isn't "does it run" It's "are the answers still correct" — so we replay every API on both databases and compare

不用記細節，抓個規模跟形狀就好。規模上，大概 39 萬筆資料、23 張表、48 支 stored procedure、橫跨 4 個資料庫——這不是幾行 SQL 能解決的量。 形狀上分三步：第一步搬 schema，把表跟 stored procedure 在 PostgreSQL 上重建；第二步搬資料，把每一筆資料從舊庫複製過來；第三步搬程式，把應用程式裡那些寫給舊資料庫的 SQL 改寫成 PostgreSQL 講的話。中間有不少新舊語法對不上的細節，這裡就不展開。 真正的重點是最後一句：難的不是「跑不跑得起來」，而是「答案對不對」。所以我們的驗證方式是——把每一支 API 在新舊兩個資料庫上各打一次，比對回傳的答案。答案一致，就代表結構和資料都搬對了。這個裁判就是下一章實驗的基礎。
Chapter 04

The comparison

那這套方法到底值不值得用？我設計了一組比較，而且實際跑完了——等一下的數字都是真實結果。 這次還多做了一件事：把當年真的上線的那次遷移也挖出來，用同一把尺打分，當作現實的對照組。 先預告一個比較意外的發現：通過率高，不代表驗證做得好。

How much method should drive it?

↓  add the full method
B  Full Superpowersthe full chain: brainstorm → plan → worktrees → TDD → review → verify
↓  keep brainstorm, swap to a lean executor
C1  Brainstorm + /goalspec w/ DoD → raw /goal loop to verifier
C2  Brainstorm + /workflowsame front half → /workflow fan-out
+  one real-world control, scored on the same rubric
D  The real migrationmanual + AI · ~1 month · shipped to production · no formal workflow

A vs rest = method beats one-liner · B vs C = full vs lean · C1 vs C2 = /goal vs /workflow · D = reality check

四個 agent run，同一個任務，差別只在方法介入多少；另外加一組真實世界的對照。 A：一句話 prompt，repo 原封不動，就是前面那個陷阱。 B：完整的 Superpowers 流程，從 brainstorming 一路到 review、驗證。 C1：保留 brainstorming 產出規格，執行端只用一個 /goal 迴圈。 C2：一樣的前半段，執行端改用 /workflow 平行展開。 D 比較特別：這不是實驗，是當年真的上線的那次遷移——人加 AI，大概一個月，沒有任何正式工作流。這次我把它的 repo 挖出來，用同一把尺打分，當作現實的對照組。 這樣可以回答四件事：A 對其他組，方法贏不贏一句話 prompt；B 對 C，全套值不值得；C1 對 C2，兩種執行方式的取捨；然後所有 agent run 對 D——跟一個月的人工迭代比，到底差在哪。 先說清楚：B 和 C 差的是一整組紀律，所以這是「全套 vs 精簡」的比較，不是單一變因；D 更是完全不同的時間尺度，等一下讀數字要記得這件事。 每一組下面都有按鈕，可以放大看實際執行的截圖。

Pre-flight checklist

Re-brief the task in five fields

  1. Goal
    Deliverable + decision, not an action
  2. Context
    What would someone new need to know?
  3. Materials
    Give the sources — don't make things up
  4. Boundaries
    Wall off anything you can't undo
  5. Definition of done
    No verifier → build it first

1–3 write the spec · 4 is isolation · 5 is the verifier — the filled-in brief is your prompt

在打 /goal 或 /workflow 之前，用五個欄位把任務重新交辦一遍。 一，目標：你要的是成品加一個決定，還是只描述了一個動作？先想清楚：這份東西出現在眼前之後，你要拿它來幹嘛。 二，背景：想像一個聰明、但對這個 repo 完全不熟的同事來接手——他需要知道什麼才不會走錯方向？缺一張地圖，就先補 CLAUDE.md。 三，素材：指給它看能用的材料——程式碼、文件、baseline。找不到的就留白，不要編造。 四，邊界：前三欄給的是方向，這一欄給牆。想一下：它做出什麼，你會說「這不是我要的」？先寫下來，把不可逆的副作用圍起來、工作區隔離好。 五，完成定義：什麼東西出現在眼前，你就可以收工？把它變成機器可檢查的——沒有 verifier 就先建 verifier 再跑。 這五欄剛好把第二章的三個洞補滿：前三欄就是規格，邊界就是隔離，完成定義就是 verifier。 五欄寫完，它就是你的 prompt，沒有花俏的技巧——拿著它交給 /goal 或 /workflow 執行。這五欄也是在量你的任務離「能自動駕駛」還有多遠。
