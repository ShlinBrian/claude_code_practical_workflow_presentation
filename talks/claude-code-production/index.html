Three layers of engineering an agent

Prompt the words
Harness ◆ today
Autopilot the destination

Today is all about the harness — because it is what earns you the autopilot that comes next

在進到今天的主軸之前，先給大家一個overview，也講清楚今天最終要把大家帶到哪。 跟 AI 一起開發，其實是一條路，三個階段，一階比一階更自主： **第一階 Prompt**：為單次互動寫出精準指令，把「這一次」的輸出做對。 **第二階 Harness**：不只是下指令， 讓任務、完成的定義、工作環境都被定義得夠清楚、agent 能自我驗證 我們都知道，這就是最麻煩的地方，所以我們可以透過一些簡單好用的工具來幫我們 今天我們的重心會放在這裡 **第三階 Autopilot 也就是這條路的終點**： 把前面這些包成一個 自主運作 的系統，就可以讓 agent 進入 自動駕駛。 自己去 pull 新任務、來回把「任務」確認清楚、自己走完整個開發週期、把任務交付出去， 然後回頭再拿下一個任務，就這樣一直loop下去。 我們把力氣花在 harness，為的就是有一天 我們真的可以通往 Autopilot。

Chapter 01

Everyday hygiene

第一章先從幾個小習慣開始，這些是今天回去馬上就能用的東西，門檻最低、回報也最快。 它們同時也是後面所有東西的基礎：context 管得乾淨、交接寫得清楚，之後 agent 才有辦法自己接手、自己跑。

You shouldn't have to repeat yourself

The pain
- Context filling up
- Usage running out
- The agent forgets an earlier decision
⇒ Need to re-explain the whole thing
→
The fix
- Shape the live context
- Hand state off before context/usage runs out
⇒ Steer it, don't restart it
（左邊亮） 大家應該都遇過：跑到一半 context 快滿了、usage 快用完了，或是 agent 忘記你前面講過的決定。 結果就是把整個任務從頭再解釋一遍，而且每次都這樣。 （第二下：右邊亮、左邊暗） 解法有兩個方向：一是在執行過程中主動控制 context，等一下的 /rewind、/btw、subagent 就是在做這件事；二是在 context 用完之前，先把狀態交接出去。 這樣你是在指揮它，而不是每次都重來。 接下來三頁就是三個時機：執行中、對話收尾前、還有 context 滿了的時候。

Keep the run on track

# wrong turn? rewind to before it — no re-explaining
/rewind → pick the <checkpoint> before the bad edit

# quick lookup you DON'T want in history — answer shows
/btw what does this driver error mean?

# offload a noisy task to a fresh context — only the result returns
create a subagent to scan all modules and return only the ones that fail

/rewind back out · /btw look up without growing context · subagent type an instruction to spin one up

這三個都是在執行過程中用的。 /rewind：發現它走錯方向，直接倒回出錯前的那個檢查點，不用重新解釋。 /btw：跑到一半想查個小問題，又不想讓它進到對話紀錄——答案會顯示在一個可以關掉的視窗裡，context 不會變大。 subagent：把吵雜的任務丟給一個新的 context，像是「掃描所有模組、只回傳失敗的那些」。token 讓 subagent 去消耗，回到主對話的只有結果。

再來是 session 收尾的時候，把值得留的東西存下來。 看上面這段對話：我請它把按鈕間距加大，看了結果覺得不錯，就再講一句「把這個間距存成規則寫進 CLAUDE.md」，它就記下來了。下次它會直接用同樣的間距，不用再講一次。 下面兩個檔案的分工：memory.md 是 Claude Code 自動累積的這一輪事實，沒有 commit；CLAUDE.md 是 commit 進 repo 的，每個新 session 一開始就會讀到。 收尾時可以直接說「把值得記住的規則整理一下」，它會幫你挑重點。不過 CLAUDE.md 要保持精簡，人工看過、只留真的值得記的，不要把整個 session 倒進去。

Chapter 02

The method

接下來進到今天的重心：方法。 不過在講方法之前，先看看不用方法會怎樣——我們都很想直接丟一句話給 agent，然後拿到可以上線的東西。 先看這種做法會留下哪三個洞，再講三個工具怎麼補。

The naive way

# the prompt most people would write:
Migrate this Java service from MSSQL to PostgreSQL.
  Keep everything working.

Looks reasonable It is a trap

這大概是多數人會打的 prompt：「把這個 Java 服務從 MSSQL 搬到 PostgreSQL，保持一切正常運作。」 看起來很合理，有任務、也有目標。

What you get back

It rewrites the SQL, swaps the driver, the build goes green — and it confidently says "done."

Three things are missing — and they're the whole game:

No spec“keep everything working” is undefined
No definition of donenothing checks the answers are still correct
No isolationit edited your working tree in place
agent 會認真地改 SQL、換 driver，build 過了，然後說「完成了」。從它的角度看，它確實完成了。 但有三個東西不見了： 一，沒有規格——「保持一切正常」沒有定義。 二，沒有完成的定義——沒有任何東西在檢查答案還對不對。 三，沒有隔離——它直接改了你的工作目錄。 這三個洞，就是接下來的方法要補的。

SuperPowers produces the spec; /goal and /workflow are two ways to execute against it

這一章就三個工具，先看全貌。 SuperPowers 負責把任務變成一份帶「完成定義」的規格；/goal 和 /workflow 是拿著規格去執行的兩種方式——一個是循環到目標達成，一個是多個 agent 平行展開。 順序就是：先定義好，再執行。

大家應該都有這種經驗：同一個需求，今天丟出去結果不錯，明天再丟一次就不行，差別常常只是那天 prompt 寫得好不好。 SuperPowers 想解決的就是這件事。它是一套用 skill 組起來的開發流程，從定義、規劃、建構到驗證，每個階段該怎麼做都寫在 skill 裡。 有人可能會想：這跟內建的 plan mode 差在哪？plan mode 是用權限做的一道關卡，只管「動手前先規劃」這一步；SuperPowers 管的是整條流程。 這樣品質就不是取決於當天的 prompt，而是取決於流程。整條流程的入口是 brainstorming，下一頁拆開來看。

★ brainstorming

Five steps, one gate at the end

01  Explore project context
↓
02  Ask clarifying questions — one at a time
↓
03  Propose 2–3 approaches with trade-offs
↓
04  Present design, approve section by section
↓
05  Commit a spec — with a Definition of Done

Refuses to write code until the design is approved That gate is the point

brainstorming 就五步：摸清專案脈絡、一次問一個問題、給兩三個方案和取捨、設計分段讓你確認、最後 commit 一份帶 Definition of Done 的規格。 重點在最後那道關卡：設計沒被確認，它就不寫 code。 它強迫的正是我們最常跳過的那一步——先想清楚再動手。前面多花十幾分鐘，換的是後面少掉的重寫和 debug。

"Migrate the DB" → a spec

"keep everything working" — define it; same API responses? Yes: the app runs on PostgreSQL and every endpoint in postman/api.json returns 2xx / a sane payload — no 500s, no DB errors

How do we verify that automatically? Run the Postman collection headless with newman, every endpoint, each run → committed: docs/superpowers/specs/…-migration-design.md (with DoD)

A committed spec with a testable DoD — exactly what /goal & /workflow consume

把剛剛那句 prompt 丟進 brainstorming 會發生什麼？ 它會反問：「保持一切正常」到底是什麼意思？還有，要怎麼自動驗證這件事？ 討論出來的答案就變成可測試的 DoD：用 newman 把 postman/api.json 裡的每支 endpoint 跑一遍，全部要回 2xx、不能有 500、不能有 DB 錯誤。 這份規格已經 commit 進 repo，按下面的按鈕可以看原文。它就是 /goal 和 /workflow 接下來要吃的輸入。

/goal — loop until the goal is met

# hand it the spec + a machine-checkable goal:
/goal Every test passes AND output matches the
  expected baseline. Spec: …design.md
build → test → check → fix → repeat until the verifier passes

Only works if the goal is machine-checkable No verifier → it loops or stops on a vibe

先講 /goal。給它規格，加上一個機器可檢查的目標，它就會一直跑 build → 測試 → 比對 → 修，直到通過為止。 限制也寫在投影片上：目標一定要機器可檢查。沒有這個裁判，它就會空轉，或是憑感覺停下來。 這也是為什麼 brainstorming 重要——它產出的規格裡，就帶著這個裁判。

/workflow — multi-agent fan-out

# you invoke it in natural language — the agent authors & runs the script:
/workflow process every independent unit in parallel, then verify each 
// process many independent units in parallel, then verify each
const units = await agent('list the work items', {schema: ITEMS})
const results = await pipeline(
  units.list,
  u => agent(`transform ${u}`, {phase: 'do',     isolation: 'worktree'}),
  c => agent(`verify ${c.id}`, {phase: 'verify', schema: VERDICT})
)
return results.filter(r => r.verdict.ok)

You say it in words — /workflow writes the deterministic script above and runs it Each unit flows do→verify independently Wall-clock = slowest chain, not the sum

/workflow 適合可以拆成很多獨立小單位、平行處理的工作。 你用自然語言下指令，它會把指令編成上面這段確定性的腳本：先列出所有工作項目，每一個在自己的 worktree 裡處理，再各自驗證。 兩個特性：時間上，整體耗時等於最慢的那一條，不是全部相加；結構上，每個單位互相隔離，一個失敗不會污染其他的。

When each fits

/goalone coherent objective · tight feedback loop · mostly sequential (build/test/fix)
/workflowmany independent units · want parallelism + isolation · deterministic structure

Hybrid (most realistic): a main-loop /goal drives the overall build/test/fix
and calls /workflow to fan out the independent units inside it

Later we'll put this choice to the test on a real task

選哪個，看工作的形狀。 /goal 適合單一明確目標、回饋循環很緊、大致線性的工作；/workflow 適合很多獨立單位、想要平行加隔離的工作。 實際上最常見的是混合：主迴圈用 /goal 推進整體，中間呼叫 /workflow 把獨立單位平行展開。 這個選擇，等一下會用真實任務的數據來看。
Evaluation · the most important part of the loop tooling

First build the verifier

Some tasks come with a verifierwhen a correct "old" answer already exists, you get an oracle for free to check against
Normal feature work does notno correct answer exists yet — the verifier is your test suite, and you have to build it
/goal and /workflow are self-verifying — they loop against a verifier So if the verifier doesn't exist yet, build the verifier first — it's step one, not the last step Thin coverage → the loop is blind, and you can't trust anything it ships

Anthropic's line: if you can't verify it, don't ship it

這裡有一個前提要先講清楚。 /goal 和 /workflow 都是靠裁判在自我驗證，所以它們的可靠度，就等於你給它的那個裁判的可靠度。 有些任務的裁判是現成的——舊系統的正確答案本來就存在，拿來比對就好。等一下第三章的案例就是這種。 但平常的功能開發沒有現成答案，裁判就是你的測試，而且要自己先蓋出來。 所以驗證器是第一步，不是最後一步。測試覆蓋不夠，這個迴圈就是在盲跑，跑出來的東西你沒辦法信。 Anthropic 的說法是：驗證不了的東西，就不要出貨。
Chapter 03

The case

方法講完了，大家可能會想：這在真的很難的任務上行得通嗎？ 接下來用一個我實際做完的案例來看難度在哪。

Not a "swap the JDBC driver" job

What

A years-old commercial download backend, still in production — real users every day Moved MSSQL → PostgreSQL: data, schema, stored procedures, dialect SQL in Java/JSP

The bar

Every API must return the correct response on PostgreSQL A wrong answer ships to real customers

The shape

Difficulty stacks in two phases: Phase A · migrate the schema, then Phase B · migrate the data

先講清楚這個案子是什麼。這不是換個 driver 就好的事。 這是一個跑了很多年、還在線上的商用下載後端，每天都有真實用戶在用。整套從 MSSQL 搬到 PostgreSQL：資料、schema、stored procedure，還有埋在 Java/JSP 裡的方言 SQL。 標準只有一個：每支 API 在 PostgreSQL 上都要回傳正確的結果，因為錯的答案會直接送到用戶手上。 工作分兩個階段：Phase A 搬 schema，Phase B 搬資料。

What had to move

~390k rows across 23 tables · 48 procs + 4 views · 4 databases

規模大概是這樣：39 萬筆資料、23 張表、48 支 procedure 和 function、4 個 view，橫跨 4 個資料庫。 數字不用記，只要知道這不是幾行 SQL 能解決的量。

The hard part isn't "does it run" It's "is the answer still correct"

Phase A 搬 schema，難的地方我整理成四種「對不上」。 一，工具自動化不了：AWS SCT 只有 GUI，但我需要全自動跑——後來改從它的 CLI 驅動，整段無頭執行。 二，SQL 是寫給另一個引擎的：跨庫 join 和方言只有 MSSQL 吃——分析後發現程式其實只連同一個庫，所以可解。 三，stored procedure 對不上 driver：轉出來的 proc 不符合 Java driver 呼叫的形狀——全部改寫成 RETURNS SETOF 的 function。 四，識別字的大小寫規則不同：加上 TOP、ISNULL、中括號這些方言——最後統一全小寫，加 citext。 細節不用記，記一件事就好：難的不是「跑不跑得起來」，是「答案還對不對」。這也是後面那個裁判存在的理由。

Phase B 搬資料本身：用 SCT 的 BatchExecutor 從 MSSQL 匯出，載入 PostgreSQL——39 萬筆、23 張表，配合全小寫識別字和 citext。 驗證的方式值得說一下：我們不直接檢查資料有沒有搬對，而是把每支 API 在新舊兩個資料庫上各打一次，比對回傳的答案。答案一致，資料和轉換就都對了。 一個裁判涵蓋兩個階段，不用另外維護一套逐列比對。
Chapter 04

The comparison

那這套方法到底值不值得用？我設計了一組比較，而且實際跑完了——等一下的數字都是真實結果。 先預告一個比較意外的發現：通過率高，不代表驗證做得好。

How much method should drive it?

A  Naiveone-line prompt, repo as-is → the trap
↓  add the full method
B  Full Superpowersthe full chain: brainstorm → plan → worktrees → TDD → review → verify
↓  keep brainstorm, swap to a lean executor
C1  Brainstorm + /goalspec w/ DoD → raw /goal loop to verifier
C2  Brainstorm + /workflowsame front half → /workflow fan-out

A vs rest = method beats one-liner · B vs C = full vs lean · C1 vs C2 = /goal vs /workflow

四個 run，同一個任務，差別只在方法介入多少。 A：一句話 prompt，repo 原封不動，就是前面那個陷阱。 B：完整的 Superpowers 流程，從 brainstorming 一路到 review、驗證。 C1：保留 brainstorming 產出規格，執行端只用一個 /goal 迴圈。 C2：一樣的前半段，執行端改用 /workflow 平行展開。 這樣可以回答三件事：A 對其他組，方法贏不贏一句話 prompt；B 對 C，全套值不值得，還是 brainstorming 加一個驗證迴圈就夠；C1 對 C2，兩種執行方式的取捨。 先說清楚：B 和 C 差的是一整組紀律，所以這是「全套 vs 精簡」的比較，不是單一變因。 每一組下面都有按鈕，可以放大看實際執行的截圖。

Human review is the new bottleneck → force small PRs that carry their own A/B evidence Review the evidence, not every diff line

也要知道什麼時候不該直接交給 agent。 三種情況：沒有機器可檢查的裁判；有不可逆的副作用，像刪資料、呼叫外部 API、動到錢；還有，需要的領域知識根本不在 repo 裡。 另外一個提醒：人的瓶頸會從寫程式變成 review。所以讓 agent 切成自帶驗證證據的小 PR，review 的時候看證據，不用逐行看 diff。 反過來說，這三件事補齊的時候，就是可以放心讓它自己跑的時候。

Pre-flight checklist

地圖上 harness 這段已經走完了。最後給大家一張可以帶回家的清單。

Pre-flight checklist

  1. Definition of done
    Is there a machine-checkable "done"?No verifier → build the tests first, then run
  2. Goal
    Do you want a deliverable and a decision, or did you just describe one action?
  3. Boundaries
    What's off-limits?Fence irreversible side effects first
  4. Legibility
    Can the agent understand the code? Missing a map → add it first
  5. Stage
    Do you want it to think, compare, decide, or do right now?
在打 /goal 或 /workflow 之前，先問自己五件事。 一，完成的定義：有沒有機器可檢查的「完成」？沒有，就先把測試補起來再跑。 二，目標：你要的是一個交付物加一個決定，還是只描述了一個動作？ 三，邊界：什麼不能碰？先把不可逆的副作用圍起來。 四，可讀性：agent 看得懂這份程式碼嗎？缺一張地圖就先補上。 五，階段：你現在是要它思考、比較、決定，還是動手？ 哪一題答不出來，就先處理哪一題。這五題也是在量你的任務離「能自動駕駛」還有多遠。
