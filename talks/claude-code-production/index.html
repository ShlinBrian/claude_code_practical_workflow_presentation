The one idea behind everything that follows

Behind all six chapters, one idea runs through everything.

Two questions, very different leverage

“Can the agent do it?” Polishing prompts plateaus — and leaves you waiting for a better model.
vs
“Have I defined the task
and the environment
well enough that it can?” The leverage is the spec, the definition of done, and the workspace you hand it.

Everything in this talk is one of those two levers.

What it looks like on the migration task

"Migrate the DB" → a spec

"keep everything working" = same API responses, or same DB state? Same HTTP responses, byte-for-byte where data allows. How do we verify that automatically? A/B every endpoint vs a golden MSSQL, row-by-row. → committed: docs/specs/mssql-pg-migration-design.md (with DoD)

A committed spec with a testable DoD — exactly what /goal & /workflow consume.

The method, part 2 — two ways to spend tokens well

/goal — loop until the goal is met

# hand it the spec + a machine-checkable goal:
/goal Every test passes AND output matches the
  expected baseline. Spec: …design.md
build → test → check → fix → repeat until the verifier passes

Only works if the goal is machine-checkable. No verifier → it loops or stops on a vibe.

/workflow — orchestrate many agents deterministically

/workflow — multi-agent fan-out

// process many independent units in parallel, then verify each
const units = await agent('list the work items', {schema: ITEMS})
const results = await pipeline(
  units.list,
  u => agent(`transform ${u}`, {phase: 'do',     isolation: 'worktree'}),
  c => agent(`verify ${c.id}`, {phase: 'verify', schema: VERDICT})
)
return results.filter(r => r.verdict.ok)

Each unit flows do→verify independently. Wall-clock = slowest chain, not the sum.

Not rivals — pick by the shape of the work

When each fits

/goalone coherent objective · tight feedback loop · mostly sequential (build/test/fix)
/workflowmany independent units · want parallelism + isolation · deterministic structure

Hybrid (most realistic): a main-loop /goal drives the overall build/test/fix
and calls /workflow to fan out the independent units inside it.

Later we'll put this choice to the test on a real task.

Self-verifying tools — only as good as what they verify against

First build the verifier

Some tasks come with a verifierwhen a correct "old" answer already exists, you get an oracle for free to check against.
Normal feature work does notno correct answer exists yet — the verifier is your test suite, and you have to build it.
/goal and /workflow are self-verifying — they loop against a verifier. So if the verifier doesn't exist yet, building it is task zero, not task N. Thin coverage → the loop is blind, and you can't trust anything it ships.

Anthropic's line: if you can't verify it, don't ship it.

Phase A — structure + code: the semantic gap, and how each was beaten

Phase A · 4 problems → 4 fixes

SCT is GUI-only, but had to run fully automated in headless WSL
→
SCT BatchExecutor CLI + bundled Corretto 17; control codes 0x1f/0x1e as delimiters
Cross-DB joins — MSSQL 3-part names; PostgreSQL can't
→
app only uses main / main_write / downloader (all Downloader) — tractable
SCT made INOUT refcursor procs — but pgjdbc {call…} needs functions
→
rewrite to RETURNS SETOF functions; citext for case; rebuild views
Dialect + case — TOP ISNULL GETDATE() dbo. [brackets]
→
all-lowercase strategy — drop brackets so PostgreSQL folds & compares

The hard part isn't "does it run" — it's "is the answer still correct."

Phase B — once the structure runs, move the data

Phase B · migrate the data

Export from MSSQLSCT BatchExecutor · 0x1f/0x1e delimiters (never appear in the data)
→
Load into PostgreSQL~390k rows across 23 tables · all-lowercase identifiers · citext

How do we know the data landed right?
We don't check it directly — the API A/B verifier proves it.
If every endpoint matches golden MSSQL, the data and the conversion are both correct, end-to-end.

One verifier covers both phases — no separate row-by-row data audit.

Chapter 06

Pre-flight checklist

Five questions to take home

Five questions before you type /goal or /workflow

Pre-flight checklist

  1. Definition of done
    Is there a machine-checkable "done"? No verifier → build the tests first, then run.
  2. Goal
    Do you want a deliverable and a decision, or did you just describe one action?
  3. Boundaries
    What's off-limits? Fence irreversible side effects first.
  4. Legibility
    Can the agent understand the code? Missing a map → add it first.
  5. Stage
    Do you want it to think, compare, decide, or do right now?
