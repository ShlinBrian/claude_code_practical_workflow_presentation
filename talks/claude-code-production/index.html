Three layers of engineering an agent

Prompt the words
Harness ◆ today
Loop the destination

Today is all about the harness — because it is what earns you the loop that comes next

在進到今天的主軸之前，先給大家一張地圖，也講清楚今天最終要把大家帶到哪。 跟 AI 一起開發，其實是一條路，三個階段，一階比一階更自主： **第一階 Prompt Engineering**：為單次互動寫出精準指令，把「這一次」的輸出做對。大多數人都是從這裡開始的。 **第二階 Harness Engineering**：不只是下指令，而是打造 agent 運行的**環境跟護欄**——它能存取什麼、能用哪些工具、邊界在哪、規格跟完成的定義是什麼。今天大部分人的重心落在這裡，**今天整場的方法、案例、實驗，也都是在教這一階怎麼做好**。 **第三階 Loop Engineering，這才是這條路的終點**：把前面這些包成一個**定時、自主運作**的系統。 想像一個不用你盯著的 agent——它**自己去 pull** 看有沒有新任務、**收到後跟你來回把「完成」確認清楚**、**自己走完整個開發週期**（規劃、實作、測試、驗證）、**把任務交付出去**，然後**回頭再拿下一個**，一直轉下去。這就是 loop。 （指這條由左到右的路，跟中間發亮的那一段）這是一條路：從 prompt，走到 harness，再走到 loop。**中間發亮那段就是 harness——今天整場要教的，就是這一段。** 右邊的 loop 我畫得比較淡、只用一個箭頭標了「next」，因為它是**下一步**、是方向，不是今天的操作內容。 這裡我要講一個關鍵：**你不可能跳過 harness 直接做 loop。** 一個能自己跑、你又敢信任的自主迴圈，前提就是任務、完成的定義、工作環境都被定義得夠清楚、agent 能自我驗證——而那正是 harness engineering。 所以今天我們把力氣花在 harness，**不是因為它是終點，而是因為它是通往 loop 的地基**——把它做好，才有資格談右邊那個 loop。

Where do you put your energy?

Stop asking — “Can the agent do it?” Tune the prompts · switch to a better model · hit a ceiling
↓
Start asking — “Have I defined it well enough that it can?” The task, the definition of done, the workspace you hand it

Define it that well and the agent can run it on its own — that's the loop

現在的model跟去年比已經強很多了，基本上可以執行任何事情。 所以問題不是「這個 agent 夠不夠強」，而是「你把力氣花在哪裡」。 整場分享其實只有一個核心想法，就在這頁。 （第一下：上面那個問題亮） 大多數人把力氣花在上面這件事——**「這個 agent 做得到嗎？」** 於是就一直調 prompt、換更好的模型。這條路的麻煩是——它會撞到天花板，調到最後就是在等下一個更強的模型。 *換頁*（箭頭往下、下面那個問題亮、上面暗） 我想請大家把焦點往下移，改問——**「我有沒有把它定義到它做得到的程度？」** 真正的槓桿不在模型，也不在 prompt 的措辭，而在**任務本身、完成的定義、還有你交給它的工作環境**。 而且這裡還有更深一層：**當你把任務定義到這個程度，agent 就能自己把它跑完——那就是我們要走向的 loop。** 今天所有的內容，都是在幫你把力氣移到這裡、打好通往 loop 的地基。
Chapter 01

Everyday hygiene

接下來這些是**今天回去馬上就能用或改善**的小習慣。 因為這些方法門檻最低、回報最即時。

You shouldn't have to repeat yourself

The pain
- Context filling up
- usage running out
- The agent forgets an earlier decision
⇒ Need to re-explain the whole thing
→
The fix
Steer the live context while you work
Hand state off before context runs out
⇒ You steer, not restart
（左邊亮） 大家一定常常遇過跑到一半，context 快滿了，或者 usage 快沒了 或者 agent 忘記了你前面講過的決定。 結果呢？你得**把整個任務從頭再解釋一遍**——而且每次都這樣。 （第二下：右邊亮、左邊暗） 解法很直白：第一，**在跑的過程中主動控制當前的 context**（等一下的 /rewind、/btw、subagent 就是在做這件事）；第二，在 **context 用完前，把狀態交接出去**。 所以你是在**指揮**它，而不是整個**重來**。 接下來三頁，就是三個動作：你在什麼時候用它們: 1. 對話來回執行期間的時候 2. 對話結束前 3. 還有 context 滿了的時候或想使用新的agent的時候

Keep the run on track

# wrong turn? rewind to before it — no re-explaining
/rewind → pick the <checkpoint> before the bad edit

# quick lookup you DON'T want in history — answer shows
/btw what does this driver error mean?

# offload a noisy task to a fresh context — only the result returns
create a subagent to scan all modules and return only the ones that fail

/rewind back out · /btw look up without growing context · subagent type an instruction to spin one up

讓這一個session不要跑歪: 1. `/rewind`：發現它走錯了，直接倒回出錯之前的那個檢查點，**不用重新解釋**。 2. `/btw`：跑到一半想問某個當前執行問題 3. 建立一個 subagent：告訴它「掃描所有模組、只回傳失敗的那些」—— 這樣雜訊的任務交給新的 context，只有結果傳回來，不會吃掉你的 context 空間。

這頁講的是 session 結束前，如果你對操作滿意，應該存入長期記憶。 看上面這段對話： 我說「按鈕看起來太擠了，把間距加大一點」，它就幫我把按鈕之間的距離拉開。 我看了結果覺得不錯，這時候做法很簡單，直接跟 agent 講一句：「把這個間距存成規則寫進 CLAUDE.md」，它就記起來了。 重點是：這不再是這一次的調整，而是變成專案的規矩，下一次它就用同樣的間距。 再看下面兩個檔案的角色： `memory.md` 是這一輪累積的事實，**Claude Code 自動幫你建**、專案本地、沒有 commit。 `CLAUDE.md` 正好相反——commit 進去、下一次 session 一開啟就讀到，長期存在。 你可以在收尾的時候直接講一句「把值得記住的規則整理一下」，它就會幫你把這一輪的重點挑出來、整理好。 但要注意 CLAUDE.md 不能太長，需要人工審核只留那些**真的值得記住的東西**，不是把整個 session 倒進去。 這樣下一次開新 session，它一開始就知道專案的規矩，省你一遍解釋。

Chapter 02

The method

接下來是今天的核心：方法。但在講方法之前，先看看**不用方法**會怎樣—— 我們其實很想要非常簡單的丟一句話給 agent，然後期待它生出可以上線的東西。 我會先示範這種 naive 做法留下的三個洞，再講三個工具怎麼把洞補起來。 舉例來說：

The naive way

# the prompt most people would write:
Migrate this Java service from MSSQL to PostgreSQL.
  Keep everything working.

Looks reasonable It is a trap

這是大多數人會打的 prompt： 「把這個 Java 服務從 MSSQL 搬到 PostgreSQL，**保持一切正常運作**。」 看起來很合理對不對？它有描述任務、也有目標。

What you get back

It rewrites the SQL, swaps the driver, the build goes green — and it confidently says "done."

Three things are missing — and they're the whole game:

No spec“keep everything working” is undefined
No definition of donenothing checks the answers are still correct
No isolationit edited your working tree in place
1. agent 會很認真地改 SQL 2. 換掉 driver 3. build 變綠燈 4. 然後**很有自信地說「完成了」**。 從它的角度看，它真的成功了。 但： 1. **沒有規格**——「保持一切正常」根本沒有定義。 2. **沒有完成的定義**——沒有任何東西在檢查答案是不是還正確。 3. **沒有隔離**——它直接改了你的工作目錄。 這三個洞，就是接下來方法要補的東西。

這一章的核心只有三樣東西，先給大家一眼看清全局。 **SuperPowers** 負責把任務轉成帶有「完成定義」的規格； **`/goal`** 跟 **`/workflow`** 是接著執行的兩種方式——一個走「循環到目標達成」，一個走「多 agent 平行展開」。 三個工具，一條 pipeline：先定義好，再跑起來。

大家用 Claude Code 應該都有這種經驗：同一個需求，今天丟出去結果很讚，明天再丟一次就爛掉。差別往往只是那天 prompt 剛好寫得好不好。 SuperPowers 想解決的就是這件事。它其實是一套完整的軟體開發方法論 — 底層是一組可組合的 skill，再加上一些初始指令，確保你的 agent 真的會去用它們。 這裡可能有人會想：這不就是 Claude Code 內建的 plan mode 嗎？ 差別在於 — plan mode 是 Anthropic 用權限層做的『硬關卡』，把 Claude 鎖成唯讀、不准它碰檔案； 而 SuperPowers 是用 skill 疊出來的一整套流程，管的不只是『動手前先規劃』這一關，而是從定義、規劃、建構到驗證，每一步該怎麼做都寫進去。 換句話說，plan mode 是一道門，SuperPowers 是整條產線。 所以它不是教 AI 『做什麼』，而是把『怎麼做』寫死成流程 — 定義、規劃、建構、驗證，四個階段一路走下來。 品質就不再靠運氣，而是靠流程。而這整條線的入口，就是 brainstorming。下一頁我拆給大家看它到底在做什麼。

Refuses to write code until the design is approved That gate is the point

這是我最常用、最關鍵的一個 skill。它的流程就是這個垂直的圖： 先探索專案脈絡 → 一次只問你一個問題 → 提兩三個方案讓你比較 → 分段呈現設計、一段一段讓你確認 → 最後**產出一份帶有「完成定義」的規格、commit 進去**。 最關鍵的一點：**在設計被你核可之前，它拒絕寫任何程式碼。** 這個「卡住不動」就是它的價值所在。

"Migrate the DB" → a spec

"keep everything working" — define it; same API responses? Yes: the app runs on PostgreSQL and every endpoint in postman/api.json returns 2xx / a sane payload — no 500s, no DB errors

How do we verify that automatically? Run the Postman collection headless with newman, every endpoint, each run → committed: docs/superpowers/specs/…-migration-design.md (with DoD)

A committed spec with a testable DoD — exactly what /goal & /workflow consume

把剛剛那句一行的 prompt 丟進 brainstorming 會發生什麼？ SuperPowers 🦸 會反問：「保持一切正常」到底是指 API 回應一樣、還是資料庫狀態一樣？ 還有：我們要怎麼**自動驗證**這件事？ 答案是真實的 DoD：把 `postman/api.json` 裡的每一支 endpoint 用 **newman** 跑一遍， 確保全部回 2xx、沒有 500、沒有 DB 錯誤——這就是可測試的 Definition of Done。 這份規格已經提交進 repo，按「📄 See the real spec」按鈕可以直接看。 這份規格，正好就是 `/goal` 跟 `/workflow` 接下來要吃的東西。

/goal — loop until the goal is met

# hand it the spec + a machine-checkable goal:
/goal Every test passes AND output matches the
  expected baseline. Spec: …design.md
build → test → check → fix → repeat until the verifier passes

Only works if the goal is machine-checkable No verifier → it loops or stops on a vibe

方法的第二部分，是兩種「把 token 花得有價值」的方式。 先講 `/goal`。你給它規格、再給它一個**機器可檢查**的目標， 它就會一直跑「build → 測試 → 比對 → 修」這個循環，直到通過為止。 關鍵限制就寫在投影片上：**目標一定要機器可檢查。** 沒有這個「裁判」，它就會空轉，或者憑感覺停下來。 這也是為什麼前面 brainstorming 那麼重要——它產出的規格，裡面就帶著這個裁判。

/workflow — multi-agent fan-out

# you invoke it in natural language — the agent authors & runs the script:
/workflow process every independent unit in parallel, then verify each 
// process many independent units in parallel, then verify each
const units = await agent('list the work items', {schema: ITEMS})
const results = await pipeline(
  units.list,
  u => agent(`transform ${u}`, {phase: 'do',     isolation: 'worktree'}),
  c => agent(`verify ${c.id}`, {phase: 'verify', schema: VERDICT})
)
return results.filter(r => r.verdict.ok)

You say it in words; `/workflow` turns it into a deterministic script — shown below Each unit flows do→verify independently Wall-clock = slowest chain, not the sum

你用自然語言下 `/workflow` 指令，它幫你編成這段確定性的 JS 腳本 — 不會用的人才看得懂它怎麼運作。 `/workflow` 是給「可以拆成很多獨立小單位、平行處理」的工作。 這段程式碼示意的就是：把**所有要處理的工作項目**列出來， 每一個各自在自己的 worktree 裡處理，再各自驗證。 兩個關鍵特性： 時間上，整體耗時等於**最慢那一條鏈**，不是全部相加； 結構上，每個單位都在自己的 worktree 裡——一個失敗，不會污染到別的。

When each fits

/goalone coherent objective · tight feedback loop · mostly sequential (build/test/fix)
/workflowmany independent units · want parallelism + isolation · deterministic structure

Hybrid (most realistic): a main-loop /goal drives the overall build/test/fix
and calls /workflow to fan out the independent units inside it

Later we'll put this choice to the test on a real task

它們不是對手，是看工作的**形狀**來選。 `/goal`：單一明確目標、回饋循環很緊、工作大致是線性的（build/測/修）。 `/workflow`：很多獨立單位、你想要平行加隔離、流程要可控。 最實際的答案其實是**混合**：用一個主迴圈 `/goal` 推進整體流程， 中間呼叫 `/workflow` 去把那些獨立單位平行展開。 這個取捨，等一下會用一個真實任務來實際驗證。

但這裡有一個前提，我要特別點出來，因為它很容易被忽略。 `/goal` 跟 `/workflow` 都是**自驗證**的工具——它們之所以能「一直跑到通過為止」， 是因為背後有一個裁判可以一直 A/B、一直打分。 **所以這兩個工具，永遠只跟你給它的那個裁判一樣可靠。** 這裡有個陷阱：**有些任務的裁判是免費送的**—— 當「舊系統的正確答案」本來就存在，你就有一個現成的標準答案可以比對。 （等一下第三章的案例，就正好是這種任務。） 但你平常做的功能開發**沒有這種東西**——沒有現成的標準答案。 那裁判是什麼？就是你的**測試**。而且你得**自己先把它蓋出來**。 **驗證器要先蓋出來，這是第一步，不是最後一步。** 測試覆蓋不夠，這個迴圈就是瞎子在跑——它跑出來的東西你一個都不能信。 這也正好呼應 Anthropic 那句話：**「如果你沒辦法驗證它，就別讓它出貨。」**
Chapter 03

The case

講了方法，大家可能會想：這在「真的很難」的任務上撐得住嗎？ 所以接下來用一個我**實際做完**的案例，讓大家感受難度。

Not a "swap the JDBC driver" job

What

A years-old commercial download backend, still in production — real users every day Moved MSSQL → PostgreSQL: data, schema, stored procedures, dialect SQL in Java/JSP

The bar

Every API must return the correct response on PostgreSQL A wrong answer ships to real customers

The shape

Difficulty stacks in two phases: Phase A · migrate the schema, then Phase B · migrate the data

先說清楚規模。這不是換個 driver 就好。 這是一個跑了很多年、至今還在線上的商用下載後端——**真實用戶每天都在用**——整套從 Microsoft SQL Server 搬到 PostgreSQL。 包含資料、schema、stored procedure，還有**埋在 Java/JSP 裡的方言 SQL**。 而且標準很硬：**每一支 API 在 PostgreSQL 上都要回傳正確的結果才算數。錯誤的答案會直接送到真實用戶手上。** 難度分兩個 Phase 疊上去——先是 **Phase A：搬 schema（結構 + 程式碼）**，再來是 **Phase B：搬資料**。

What had to move

~390k rows across 23 tables · 48 procs + 4 views · 4 databases

先看規模。大約 **39 萬筆資料**、分散在 **23 張表**，加上 **48 支 procedure / function 和 4 個 view**，橫跨 **4 個資料庫**。 這夠大、讓人一眼看出「這不是三行 SQL 的活兒」，但重點不是讓你去記每個細節，而是看整個規模的信號。

The hard part isn't "does it run" It's "is the answer still correct"

這就是 **Phase A——搬 schema**，也就是語意落差的核心。我把它整理成**四種「對不上」**，每一種都解掉了—— 細節你不用記，記住「是哪一類落差」就好。 第一，**工具自動化不了**：AWS 的 SCT 只有 GUI，但我要在無頭環境全自動跑——解法是改從它的 CLI 驅動，端到端無頭。（埋的細節：BatchExecutor、Corretto 17、用資料裡不會出現的控制碼當分隔符。） 第二，**SQL 是寫給另一個引擎的**：跨庫 join 跟方言只有 MSSQL 吃——但分析後發現程式其實只連同一個庫，所以這題可解。 第三，**stored procedure 對不上驅動**：轉出來的 proc 不符合 Java 驅動呼叫的形狀——全部改寫成 `RETURNS SETOF` 的 function。（細節：原本被轉成 refcursor。） 第四，**識別字大小寫折疊方式不同**：大小寫加方言（TOP、ISNULL、中括號）對不上——用「**一律小寫**」加 citext 統一。 重點是最下面這句：**難的從來不是「跑不跑得起來」，而是「答案還對不對」。** 這句話，就是後面那個「裁判」存在的理由。

Phase A 搬的是 schema（結構 + 程式碼），Phase B 搬的是資料本身。 做法很直接：用 SCT BatchExecutor 從 MSSQL export，載入 PostgreSQL——39 萬筆橫跨 23 張表，搭配全小寫識別符和 citext。 關鍵是這句：**我們不直接驗資料有沒有搬對——而是把每一支 API 在新舊兩個資料庫上都打一次，比對回傳的答案。** 答案一致，資料跟轉換就都正確。一個裁判，涵蓋兩個 Phase。

Pre-flight checklist

最後，給大家一張可以帶回家的清單。

Pre-flight checklist

  1. Definition of done
    Is there a machine-checkable "done"?No verifier → build the tests first, then run
  2. Goal
    Do you want a deliverable and a decision, or did you just describe one action?
  3. Boundaries
    What's off-limits?Fence irreversible side effects first
  4. Legibility
    Can the agent understand the code? Missing a map → add it first
  5. Stage
    Do you want it to think, compare, decide, or do right now?
在你打 `/goal` 或 `/workflow` 之前，先問自己五件事： 一，**完成的定義**——有沒有機器可檢查的「完成」？沒有裁判，就**先把測試補出來再跑**。 二，**目標**——你要的是一個交付物加一個決定，還是只是描述了一個動作？ 三，**邊界**——什麼是禁區？先把不可逆的副作用圍起來。 四，**可讀性**——agent 看得懂這份程式碼嗎？缺一張地圖，就先補上。 五，**階段**——你現在是要它思考、比較、決定、還是動手？ 任何一題你答「不知道」，那就是你該先處理的事。
