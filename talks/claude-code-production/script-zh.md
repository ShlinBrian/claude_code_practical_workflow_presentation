# 中文講稿 — Claude Code in Production（15 分鐘技術分享）

> 每一頁對應投影片的 slide index。括號是建議停留時間，總計約 15 分鐘。
> 講稿是「口語化、可直接念」的版本；粗體是建議加重語氣的地方。
> 全程節奏：開場輕快、方法段放慢、實驗段是重點、結尾收乾淨。

---

## 開場（slide 0、1、2 — 約 1.5 分鐘）

### Slide 0 — 封面（15 秒）

大家好，我是 Brian，來自 RD-CL.com。
今天這個分享叫「Claude Code in Production」，副標是 **一套實際可用的 RD 工作流**。
我不打算講「AI 有多強」這種東西，而是要分享一個**我自己每天在用、而且可以直接複製**的流程。

### Slide 1 — Agenda（25 秒）

先看一下今天的路線。
我會從**最簡單、你今天回去就能用**的日常習慣開始；
接著示範一個大家最常犯的錯誤——丟一句話給 agent；
然後進到核心的**方法**：skills、brainstorming，還有 `/goal` 跟 `/workflow`；
再用一個**真實的資料庫遷移案例**讓大家感受難度；
最後是我設計的一組**實驗**，跟一張可以帶回家的**檢查清單**。
每一章前面都會有一頁過場，讓大家知道我們走到哪。

### Slide 2 — 兩個問題，槓桿差很多（35 秒）

整場分享其實只有一個核心想法，就在這頁。
大多數人面對 agent 會問左邊這個問題：**「這個 agent 做得到嗎？」**
這個問題的麻煩是——它會卡住。你只能一直調 prompt，調到最後就是在等下一個更強的模型。
我想請大家換成右邊這個問題：**「我有沒有把任務跟環境，定義到它做得到的程度？」**
真正的槓桿不在 prompt 的措辭，而在**規格、完成的定義、還有你交給它的工作環境**。
等一下整場你會看到的每一招，都是在拉這兩個槓桿其中之一。

## 第一章：日常習慣（slide 3、4/0、4/1、4/2 — 約 2 分鐘）

### Slide 3 — 過場：Everyday hygiene（10 秒）

我們先從最便宜的勝利開始——這些是**你今天回去、下一個 session 就能用**的小習慣。
故意放在最前面，因為這幾招門檻最低、回報最即時。

### Slide 4/0 — 一個我們常付兩次的稅（30 秒）

先講一個大家一定遇過的痛點。
跑到一半，context 滿了；或者 agent「忘記」了你前面講過的決定。
結果呢？你得**把整個任務從頭再解釋一遍**——而且每次都這樣。
這就像一筆你一直在重複付的稅。
右邊是解法：幾個簡單的習慣，讓「狀態」變得很便宜就能恢復——
這樣你是在**操控**它，而不是一直在**重新講故事**。

### Slide 4/1 — 讓這一輪不要跑歪（40 秒）

三個動作，我直接給你怎麼用，不是只講名字。
第一，`/rewind`：發現它走錯了，直接倒回出錯之前的那個檢查點，**不用重新解釋**。
第二，`/btw`：跑到一半想補一個事實，不用打斷它——
比如「staging 資料庫是唯讀的，絕對不要寫入」，一句話塞進去就好。
第三，session 結束前，把 `memory.md` 裡的長期事實**整理進 `CLAUDE.md`**——
這樣下一次開新的 session，它一開始就知道專案的規矩，你不用再從頭講。

### Slide 4/2 — context 滿了：交接給新 agent（40 秒）

最後一招最實用：當 context 真的滿了，**不要硬撐、不要重講——直接交接**。
流程很簡單：
先寫一份 `handoff.md`——做完了什麼、接下來要做什麼、有哪些關鍵決定跟限制；
然後 `/clear` 或開一個全新的 agent，把那個臃腫的 context 丟掉、成本歸零；
新的 agent 讀完 `handoff.md` 就能**冷啟動接手**，完全不用你重新解釋整個任務。
下面這個就是 handoff 的長相——你看，它就是一份很短的交接筆記。

## 第二章：錯誤示範（slide 5、6/0、6/1 — 約 1.5 分鐘）

### Slide 5 — 過場：The naive way（10 秒）

好，習慣講完了。接下來我們看一個大家最常犯的錯——
丟一句話給 agent，然後期待它生出可以上線的東西。

### Slide 6/0 — 「就把資料庫搬一搬」（30 秒）

這是大多數人會打的 prompt：
「把這個 Java 服務從 MSSQL 搬到 PostgreSQL，**保持一切正常運作**。」
看起來很合理對不對？它有描述任務、也有目標。
但它其實是個陷阱。我先把它標成實驗裡的 **A 組**，等一下會回來。

### Slide 6/1 — 你會拿回什麼（50 秒）

agent 會很認真地改 SQL、換掉 driver，build 變綠燈，然後**很有自信地說「完成了」**。
從它的角度看，它真的成功了。
問題是有三個洞，這三個洞才是重點，我用圖呈現：
第一，**沒有規格**——「保持一切正常」根本沒有定義。
第二，**沒有完成的定義**——沒有任何東西在檢查答案是不是還正確。
第三，**沒有隔離**——它直接改了你的工作目錄。
這三個洞——沒規格、沒 DoD、沒隔離——正好就是後面整套方法要補起來的東西。

## 第三章：方法（slide 7 ~ 9/2 — 約 4 分鐘）

### Slide 7 — 過場：The method（10 秒）

接下來是今天的核心：我怎麼把這三個洞補起來。
分兩部分——先講 skills，再講 `/goal` 跟 `/workflow`。

### Slide 8/0 — Skills 對應到開發生命週期（35 秒）

先說什麼是 skill。skill 不是 prompt——它把一段**流程**編碼起來，
告訴 agent 「**怎麼做**」，而不只是「做什麼」。
左邊是「定義跟規劃」：brainstorming、writing-plans、用 git worktree 隔離；
右邊是「實作跟驗證」：用 subagent 跑 TDD、系統化除錯、code review、最後驗證。
重點是：品質不再取決於你今天剛好有沒有把 prompt 寫好——好流程變成預設值。

### Slide 8/1 — brainstorming（40 秒）

這是我最常用、最關鍵的一個 skill。它的流程就是這個垂直的圖：
先探索專案脈絡 → 一次只問你一個問題 → 提兩三個方案讓你比較 →
分段呈現設計、一段一段讓你確認 → 最後**產出一份帶有「完成定義」的規格、commit 進去**。
最關鍵的一點：**在設計被你核可之前，它拒絕寫任何程式碼。**
這個「卡住不動」就是它的價值所在。

### Slide 8/2 — 「搬資料庫」變成一份規格（35 秒）

把剛剛那句一行的 prompt 丟進 brainstorming 會發生什麼？
它會反問：「保持一切正常」到底是指 API 回應一樣、還是資料庫狀態一樣？
還有：我們要怎麼**自動驗證**這件事？
答案——把每一支 endpoint 拿去跟一份「黃金 MSSQL」逐列比對——
就變成一份有**可測試 DoD** 的規格。
這份規格，正好就是 `/goal` 跟 `/workflow` 接下來要吃的東西。

### Slide 8/3 — 規劃，然後系統化除錯（30 秒）

再補兩個你會一直重複用到的 skill。
**writing-plans**：把規格切成一個個小的、可以獨立測試的任務，每個都有檔案、測試、commit。
**systematic-debugging**：壞掉的時候，強迫你走「重現 → 隔離 → 假設 → 修 → 驗證」，而不是亂猜。
兩個的共同精神都是一樣的：**把流程編碼起來**，品質就不再看當天 prompt 的運氣。

### Slide 9/0 — `/goal`：循環到目標達成（40 秒）

方法的第二部分，是兩種「把 token 花得有價值」的方式。
先講 `/goal`。你給它規格、再給它一個**機器可檢查**的目標，
它就會一直跑「build → 測試 → A/B 比對 → 修」這個循環，直到通過為止。
關鍵限制就寫在投影片上：**目標一定要機器可檢查。**
沒有這個「裁判」，它就會空轉，或者憑感覺停下來。
這也是為什麼前面 brainstorming 那麼重要——它產出的規格，裡面就帶著這個裁判。

### Slide 9/1 — `/workflow`：多 agent 平行展開（40 秒）

`/workflow` 是給「可以拆成很多獨立小單位、平行處理」的工作。
這段程式碼示意的就是：把 **48 個 stored procedure** 列出來，
每一個各自在自己的 worktree 裡轉換，再各自做 A/B 驗證。
兩個關鍵特性：
時間上，整體耗時等於**最慢那一條鏈**，不是全部相加；
結構上，每個轉換都在自己的 worktree 裡——一個 proc 失敗，不會污染到別的。

### Slide 9/2 — 什麼時候用哪個（35 秒）

它們不是對手，是看工作的**形狀**來選。
`/goal`：單一明確目標、回饋循環很緊、工作大致是線性的（build/測/修）。
`/workflow`：很多獨立單位、你想要平行加隔離、流程要可控。
最實際的答案其實是**混合**：用一個主迴圈 `/goal` 推進整體流程，
中間呼叫 `/workflow` 去把 48 個 proc 平行展開。
等一下實驗裡的 C1 跟 C2，就是用真實數據來回答這個選擇。

### Slide 9/3 — 先把裁判蓋出來（40 秒）

但這裡有一個前提，我要特別點出來，因為它很容易被忽略。
`/goal` 跟 `/workflow` 都是**自驗證**的工具——它們之所以能「一直跑到通過為止」，
是因為背後有一個裁判可以一直 A/B、一直打分。
**所以這兩個工具，永遠只跟你給它的那個裁判一樣可靠。**
這裡有個陷阱：我那個遷移案例，裁判是**免費送的**——
因為有一份黃金 MSSQL，每一支 endpoint 早就有正確答案可以比對。
但你平常做的功能開發**沒有這種東西**——沒有現成的標準答案。
那裁判是什麼？就是你的**測試**。而且你得**自己先把它蓋出來**。
所以順序是：如果裁判還不存在，**先補測試就是第零件事，不是第 N 件事**。
測試覆蓋不夠，這個迴圈就是瞎子在跑——它跑出來的東西你一個都不能信。
這也正好呼應 Anthropic 那句話：**「如果你沒辦法驗證它，就別讓它出貨。」**

## 第四章：真實案例（slide 10 ~ 11/2 — 約 2.5 分鐘）

### Slide 10 — 過場：The case（10 秒）

講了方法，大家可能會想：這在「真的很難」的任務上撐得住嗎？
所以接下來用一個我**實際做完**的案例，讓大家感受難度。

### Slide 11/0 — 這不是「換個 JDBC driver」（35 秒）

先說清楚規模。這不是換個 driver 就好。
這是一個跑了很多年的商用下載後端，要整套從 Microsoft SQL Server 搬到 PostgreSQL——
包含資料、schema、stored procedure，還有**埋在 Java/JSP 裡的方言 SQL**。
而且標準很硬：**每一支 API 在 PostgreSQL 上都要回傳正確的結果才算數。**
難度疊在兩個面向上——**規模**，跟**語意落差**。

### Slide 11/1 — 要搬的東西（30 秒）

先看規模。
主資料庫 Downloader：18 張表、將近 38 萬筆；
另外還有 Cyberlink、PC、PMS 幾個庫。
還有 **48 支 stored procedure / function，加上 4 個 view**。
這些不是估的，是實際搬完、跟來源核對過的數字。

### Slide 11/2 — 四個難題，四個解法（60 秒）

這頁是語意落差的核心——四個難題，跟我怎麼一個個解掉的。
第一，AWS 的 SCT 工具**只有 GUI**，但我要在無頭的 WSL 裡全自動跑——
解法是用它的 BatchExecutor CLI 加內附的 Corretto 17，再用資料裡絕不會出現的控制碼當分隔符。
第二，**跨庫 join**：MSSQL 可以三段式跨庫，PostgreSQL 不行——
分析之後發現程式其實只用三個連線、而且都連同一個庫，所以這題其實可解。
第三，SCT 把回傳結果集的 proc 轉成了 refcursor，但 Java 的 pgjdbc 需要的是 function——
所以全部改寫成 `RETURNS SETOF` 的 function，用 citext 還原大小寫不敏感，再重建 view。
第四，方言加大小寫——TOP、ISNULL、中括號那些——用「**一律小寫**」的策略統一處理。
重點是最下面這句：**難的從來不是「跑不跑得起來」，而是「答案還對不對」。**
這句話，就是後面那個「裁判」存在的理由。

## 第五章：實驗（slide 12 ~ 13/4 — 約 2.5 分鐘）

### Slide 12 — 過場：The experiment（10 秒）

那麼——這套方法，到底值不值得採用？
我設計了一組實驗來回答。先說清楚：實驗**設計好了，但還沒跑**，所以結果是預留的。

### Slide 13/0 — 方法該介入多少？（50 秒）

四個 run，**同一個任務**，差別只在「方法介入多少」。
A 組：一句話 prompt，repo 原封不動——就是前面那個陷阱。
B 組：完整的 Superpowers 流程——brainstorming、writing-plans、worktree、subagent TDD、除錯、review、驗證，全套。
C1 組：保留 brainstorming 產出規格，但執行端只用一個單純的 `/goal` 迴圈。
C2 組：一樣的前半段，但執行端改用 `/workflow` 平行展開。
這樣可以同時回答三件事：
A 對其他組——方法贏不贏一句話 prompt；
B 對 C——**全套**方法值不值得，還是 brainstorming 加一個驗證迴圈就夠了；
C1 對 C2——`/goal` 跟 `/workflow` 的取捨。
誠實地講：B 跟 C 差在一**整組**紀律，所以這是「全套 vs 精簡」的比較，不是單一變因。

### Slide 13/1 — 裁判 = 完成的定義（30 秒）

這頁是讓「完成」變客觀的關鍵。
裁判就是：把 PostgreSQL 的回應，跟黃金 MSSQL 的回應，**逐 endpoint、逐列做 A/B 比對**。
沒有這個機器可檢查的裁判，「循環到目標達成」根本沒有意義。
B、C1、C2 共用同一個裁判。

### Slide 13/2 — 怎麼比較（30 秒）

四個指標：
**正確性**——裁判的通過率；
**成本**——一個好懂的總量，不用加權公式；
**完成時間**——從丟出任務到拿到可信結果的牆鐘時間；
**程式碼品質**——最後另外開一個 review agent 來打分。
給大家一個錨點:這類遷移我**以前手動做過一次**、用比較弱的模型，大概花了**一個月**。

### Slide 13/3 — 結果（待補）（20 秒）

結果就放在這張表，四個 run 乘四個指標。
現在全部標 TBD——因為實驗設計好了，還沒跑。
等跑完，這裡就會填上真實數字，還有一張 A/B 比對報告的截圖。

### Slide 13/4 — 什麼時候「不要」自動化（30 秒）

最後這頁同樣重要：知道什麼時候**不該**直接交給 agent。
三種情況：沒有機器可檢查的裁判；有不可逆的副作用——刪資料、呼叫外部 API、動到錢；
還有，需要的領域知識根本不在 repo 裡。
另外提醒一句:人的瓶頸從「寫程式」變成「review PR」——
所以要強迫 agent 切成**自帶 A/B 證據的小 PR**，讓人看證據，而不是逐行看 diff。

## 第六章 + 收尾（slide 14、15、16 — 約 1.5 分鐘）

### Slide 14 — 過場：Pre-flight checklist（10 秒）

最後，給大家一張可以帶回家的清單。

### Slide 15 — 五個起飛前的問題（40 秒）

在你打 `/goal` 或 `/workflow` 之前，先問自己五件事：
一，**完成的定義**——有沒有機器可檢查的「完成」？沒有裁判，就**先把測試補出來再跑**。
二，**目標**——你要的是一個交付物加一個決定，還是只是描述了一個動作？
三，**邊界**——什麼是禁區？先把不可逆的副作用圍起來。
四，**可讀性**——agent 看得懂這份程式碼嗎？缺一張地圖，就先補上。
五，**階段**——你現在是要它思考、比較、決定、還是動手？
任何一題你答「不知道」，那就是你該先處理的事。

### Slide 16 — 收尾（30 秒）

收在這張圖：一套可以複製的工作流——
**brainstorm → 規格加 DoD → `/goal` 或 `/workflow` → 用裁判驗證**，明天就能用。
真正值得做的轉變是:從一個「執行者」，
變成那個**定義任務、並且讓程式碼變得可讀**的人。
這兩件事是 agent 取代不了的，而且你每投資一分，都會隨著模型變強而**複利**。
謝謝大家，這部分如果有問題我們可以一起討論。
