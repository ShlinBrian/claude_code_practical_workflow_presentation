MSSQL → PostgreSQL migration: five ways to run the same job

One task — port the CyberLink product-download backend from SQL Server to PostgreSQL — executed five times, each under a different amount of workflow discipline. This report reconstructs each run from its committed artifacts (verifier output, telemetry, commit history, and the actual converted code) and scores them on the same rubric. Every quality claim below is backed by a real excerpt with a file path and line number, pulled read-only from the branch.

A · naive one-line prompt, repo as-is   B · superpowers-end-to-end full chain (brainstorm→plan→worktrees→TDD→debug→review→verify)   C1 · superpowers-goal brainstorm + /goal loop   C2 · superpowers-workflow-2 brainstorm + /workflow fan-out   D · develop real manual + AI-agent, ~1 month, no formal workflow

Read this before the scores. The brief describes the job as “verified by a per-endpoint, per-row A/B comparison against a golden MSSQL response.” That row-level verifier does not exist in any of the five branches. Every committed Postman/newman run reports "assertions": {"total": 0} — i.e. the collections contain zero pm.test() assertions and pass/fail was judged externally by HTTP status code. The only content-level check anywhere is arm B’s table-level COUNT(*) parity (row counts, not row values). So “correctness” below means, at best, “endpoint returns 2xx” + (for B) “row counts match” — not field-by-field A/B equivalence. This is the single most important caveat in the whole comparison, and it is true across all arms including the disciplined ones.

How to read the code-quality composite. Each arm is scored 1–5 on four dimensions — correctness robustness, tests, structure & readability, review trail — and the composite is their mean. Ranking: B 3.1 > D 2.9 > C2 2.5 > C1 2.25 > A 2.0. The disciplined end-to-end run (B) tops it — but the unstructured month-long human+AI run (D) lands a very close second, and tests + review are weak in every arm. The workflow’s payoff shows up as documentation, root-cause rigor, and reproducibility, not as a magically better safety net.

B · superpowers-end-to-end — most rigorous process; best documentation  composite 3.1

robustness 4.5 tests 2.5 structure 3.5 review 2

Verdict. This is the run that understood the problem. It produced a grepped dialect inventory before touching code, and its Phase-6 fix file carries the single best root-cause write-up in the whole experiment — a precise explanation of why SCT’s refcursor procedures break the app’s JDBC calls. That rigor earns the top robustness score. It’s held back by the same structural gaps as everyone else — no independent review (only an author self-review), no row-level verifier — and by a bloated 232k-line diff and a case-folding choice (LOWER() everywhere) that’s functionally correct but harder on indexes than citext.

Root-cause rigor — the refcursor/pgjdbc impedance, in the code

-- migration/phase6-fix-views-and-functions.sql:1  (header comment, verbatim)
-- Root cause (introduced by Task 3.5 schema consolidation):
--  * SCT converted the MSSQL result-set stored procedures into PG PROCEDUREs
--    with INOUT refcursor params. The legacy Java JDBC code calls them as
--    `{call Proc(?...)}` + executeQuery(). pgjdbc (default
--    escapeSyntaxCallMode=select) rewrites `{call f(?)}` to
--    `SELECT * FROM f(?)`, which requires a FUNCTION whose arg list matches
--    the Java arg count (NO refcursor) and that returns rows.

No other arm articulates why the rewrite is necessary. This is the difference between fixing a symptom and understanding the system.

C1 · superpowers-goal — cleanest diff, but the output isn’t in the repo  composite 2.25

robustness 3 tests 2 structure 3 review 1

Verdict. The /goal loop produced the smallest, tidiest change set (+1,784 lines) and a genuinely clever converter that introspects each refcursor query to discover its output columns. The fatal flaw for reproducibility: the 48 converted PL/pgSQL functions were generated live into the running database and never committed. Fast and clean, but you can’t audit or redeploy what isn’t there.

The clever bit — column discovery by introspection

# docs/migration/convert_query_procs.py:1  (docstring, verbatim)
"""Phase 3/6: convert SCT-generated refcursor PROCEDURES (query type) into
table-returning FUNCTIONS so the app's `{call proc(?)}`+executeQuery() works
(pgjdbc rewrites {call f(?)} -> SELECT * FROM f(?)). The app reads only the
FIRST result set, so we wrap the FIRST `OPEN cur FOR ` as RETURN QUERY.
Output columns are discovered by introspecting the query with params bound NULL."""

Same hard case, five solutions — side by side

Case-folding / case-insensitive comparison

MSSQL string comparison is case-insensitive by default; PostgreSQL is not. Two camps emerged: fix it at the type level (citext) or at every predicate (LOWER()). Type-level wins on correctness-by-default and index behavior.

Correct, but LOWER(col) defeats a plain b-tree index unless a matching expression index exists; and it must be applied at every comparison site — easy to miss one.

Case-insensitivity becomes a property of the data, not a rule the author must remember at each query. This is why A/C2/D score higher on this specific case.

refcursor → function rewrite

AWS SCT converts MSSQL result-set procedures into PG procedures with INOUT refcursor params. But the legacy Java calls {call proc(?)} + executeQuery(), and pgjdbc (escapeSyntaxCallMode=select) rewrites that to SELECT * FROM proc(?) — which needs a table-returning FUNCTION, not a refcursor procedure. Every arm had to bridge this. They differ in how completely, how it’s documented, and whether the output is even in the repo.

What the experiment actually shows

1. The workflow’s payoff is understanding and reproducibility, not a magic safety net. B (full chain) wins code quality because it inventoried the dialect before editing, documented the refcursor/pgjdbc root cause better than anyone, and committed a coherent plan→spec→fix trail. That is the thesis working. But no arm — not even B — built the row-level A/B verifier the brief assumes, and no arm has an independent review artifact. Discipline raised the floor on comprehension; it did not, in this dataset, produce a real automated correctness gate.

2. A month of human+AI iteration is a strong baseline. D, with no formal workflow, is second on quality and first on structure and case-folding — because real production traffic and 54 incremental commits did work that a single continuous run couldn’t. It also shipped a bug (SQLSTATE 55006) that only production caught, which is exactly the failure mode a verifier would have prevented. D is the “quality still depends on luck (and time-in-production)” control case.

3. The cheap/fast arms trade completeness for speed. C2 did the job for ~¼ the tokens with the most auditable artifacts, but leaked MSSQL syntax into legacy Java and squashed everything into one commit. C1 was the smallest, cleanest diff but never committed its own output. Fast and cheap, thinner safety.

4. “Correctness” is softer than any report claims. 47/47, 41/47, 40/40 — all are HTTP-status smoke tests (assertions: 0). The honest, uniform statement is: every endpoint returns 2xx (and for B, row counts match across 326 tables). Field-by-field A/B equivalence against golden MSSQL was not measured by any arm.
